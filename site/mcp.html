The sketch tool

excalix mcp is an MCP server over stdio with exactly one tool. An agent passes an architecture topology to sketch, and gets back the paths it wrote and the picture itself.

What the agent reads

First the server's instructions, which the client receives when it connects. With tool search on, as Claude Code has it by default, they are the only excalix text an agent sees at the start of a session, so they say when to reach for the tool:

excalix draws architecture, system and topology diagrams in Excalidraw's hand-drawn style. Use its sketch tool whenever someone asks for one, or for an Excalidraw diagram of a system: you give the nodes, edges and groups, and it picks every shape, colour and route. It writes .excalidraw, .svg and .png files and returns their paths and the image, which you should look at before reporting back. Past about twenty nodes, draw an overview and a detail diagram instead of one.

Then the tool description, the whole guide the agent gets unless the skill is installed too. It is served verbatim from tools/list:

Draws an architecture diagram. You give the topology, what exists and what talks to what; excalix picks every shape, colour, size and route, so there is nothing visual to configure.

A node sits in exactly one group: name the group it runs in, and let an edge across the boundary carry any other relationship.

List nodes in reading order, sources first. Where edges form a loop, order decides which arrow runs backwards: the one from a node listed later to one listed earlier. Among siblings it is a preference and no more, and the layout reorders some of them when that keeps arrows from crossing. It never steers where an arrow is routed; what moves a layout is the direction of an edge, which nodes share a group, and direction itself.

Look at the returned image, and act on the notes when the result has any; call again with an adjusted spec if labels overlap or the flow reads wrong.

Those are excerpts. Between them the description defines the six node kinds and two edge styles and gives the sizing advice from the spec reference. The full text and both schemas live in the contract snapshot, and the instructions in their own; the test suite keeps both in step with the server.

Input

The input schema is the spec, unchanged, plus one optional field:

fieldmeaning
the spectitle, direction, groups, nodes and edges, as in the spec reference. Only nodes is required.
outOutput basename without extension; writes <out>.excalidraw, <out>.svg and <out>.png. Relative paths resolve against the first root the client declares through MCP roots, usually the project directory. When the client declares no roots, or the request fails or takes over two seconds, the server's working directory stands in, which is the project directory when Claude Code launches the server. Absolute paths are used as given. Defaults to diagrams/<title slug>, or diagrams/diagram with no title.

Every object in the schema sets additionalProperties: false, and each field carries a description written for the model reading it.

A successful result

A call with the order pipeline spec and no out comes back as structured content and two content blocks. The paths are absolute; here the project lives in /path/to/project.

Structured content

The written paths as fields, plus the PNG's size, matching the tool's output schema:

pixels is the size of the PNG on disk, and preview the size of the image block. A very wide pixels.width usually means a long node label stretched the layout. When there is something to act on before the diagram is shown, such as a size too big to read, a notes array holds one line per thing; see large diagrams. Without anything to say, the field is absent.

A text block

The structured content again, serialized as JSON on one line. Claude Code shows the model the image and the structured content and drops text blocks, while some clients read only the content, so each carries the whole answer.

An image block

The diagram as a PNG, base64 encoded with mimeType image/png, so the agent can look at it without a separate read and call again if a label collides or the flow reads backwards. It is exported again at whatever scale up to the file's own fits 2000 pixels a side, the most Claude Code passes to a model whole, so the payload stays small and what the model sees is the image the size note judges. A diagram that already fits gets the file itself. The .png on disk stays the full 2x export, for a closer look at a detail.

Errors

A spec that fails validation does not throw a protocol error. The result has isError: true and one text block with every problem on its own line, the same lines excalix validate prints:

Anything else that goes wrong while drawing comes back the same way, as a single line starting error:. The one most people meet first:

After an error of that kind the server closes its browser and opens a fresh one on the next call. A call to any tool name other than sketch gets a protocol error instead.

Large diagrams

When the copy of the image a model reads would shrink edge labels below about 11 pixels, the result carries a note. That copy is what Claude Code hands over, fitted into 2000 pixels a side, and then what the model's high-resolution tier keeps of it, about 4784 tiles of 28 by 28 pixels; a long strip is shrunk by its edge and a dense square by its area:

Past that point thin lines and small labels go missing from what the model sees, even though the PNG on disk is sharp. The usual answer is two diagrams: an overview that collapses each region to one node, and a detail diagram of the part under discussion.
